# Portfolio audit — July 2026

Snapshot of `main` at `0b6d9f1`, after the Next 16 / Tailwind 4 / Prisma 7 upgrade
round. Covers dependency vulnerabilities, bugs, dead code, architecture, and
feature ideas.

Baseline health: `pnpm lint`, `pnpm typecheck`, and `pnpm build` all pass clean.
16 routes, all Static or SSG. Nothing here is on fire.

Everything in the dependency section was verified by running it — the numbers are
measured, not estimated.

---

## 1. Dependencies and vulnerabilities

### Where it stands

`pnpm audit` reports **34 advisories** (19 high, 14 moderate, 2 low — pnpm's
banner says 35 because one CVE is double-counted across two ranges). Every single
one is transitive. Zero come from a package listed directly in `package.json`.

### What actually closes them

I reproduced the fix in a scratch copy of `package.json` + `pnpm-lock.yaml` and
re-audited after each step:

| Step | Change | Advisories left |
|---|---|---|
| 0 | baseline | **34** |
| 1 | `pnpm update` (lockfile refresh only, no manifest edit) | **16** |
| 2 | `next` `16.2.10` → `16.2.12` | **7** |
| 3 | `pnpm.overrides` for `postcss` and `sharp` | **3** |

After all three steps `pnpm lint`, `pnpm typecheck`, and `pnpm build` still pass,
and the route table is byte-identical (verified against a full copy of `src/`).

#### Step 1 — `pnpm update`

This is the big one and it costs nothing: no manifest change, no version bumps you
have to reason about. 18 advisories disappear purely because the lockfile was
holding stale resolutions for transitive packages whose parents' semver ranges
already allow the patched versions:

| Package | Locked | Available in-range | Advisories cleared |
|---|---|---|---|
| `js-yaml` (via `gray-matter`) | 3.14.1 | 3.15.0 | 3 |
| `minimatch` (via `eslint-plugin-import`) | 3.1.2 | 3.1.5 | 3 |
| `picomatch` (via `@next/eslint-plugin-next`) | 2.3.1 | 2.3.2 | 2 |
| `flatted` (via `eslint`) | 3.3.1 | 3.4.3 | 2 |
| `brace-expansion` (via `eslint`) | 1.1.11 | 1.1.16 | 2 |
| `@babel/core` + `@babel/helpers` | 7.25.x | 7.29.7 | 2 |
| `yaml` (via `next-mdx-remote`) | 2.5.1 | 2.8.4 | 1 |
| `mdast-util-to-hast` (via `rehype-pretty-code`) | 13.2.0 | 13.2.1 | 1 |
| `fast-uri` (via `prisma`) | 3.1.3 | 3.1.4 | 1 |

Worth adding a periodic `pnpm update` (or Dependabot/Renovate on the lockfile) so
this doesn't silently accumulate again — a third of the alert count was just lock
drift.

#### Step 2 — bump Next

`next@16.2.10` carries **9 advisories** (4 high, 5 moderate), all fixed in
`16.2.11`:

- Middleware / proxy bypass in App Router (high)
- SSRF in Server Actions on custom deployments (high)
- SSRF in rewrites via attacker-controlled input (high)
- DoS in App Router via Server Actions (high)
- Cache confusion of response bodies (moderate, ×2)
- Unbounded Server Action payload in Edge runtime (moderate)
- DoS in the Image Optimization API (moderate)
- Unauthenticated disclosure of internal Server Function endpoints (moderate)

Relevance to this site is mostly low — it's static, has no middleware, no
rewrites, and one server action — but three of these touch Server Actions and this
site ships two (`sendEmailAction`, `recordPostViewAction`). `16.2.12` is a patch
bump with no migration; take it.

Bump `eslint-config-next` to `16.2.12` in the same commit to keep them in lockstep.

#### Step 3 — overrides for `postcss` and `sharp`

These two cannot be fixed by updating, and it's worth understanding why before
reaching for an override:

- **`next` pins `postcss` to exactly `8.4.31`.** Not a range — an exact pin. So no
  amount of `pnpm update` moves it. Three advisories (2 high, 1 moderate): arbitrary
  file read and path traversal via source-map auto-loading, plus XSS via an
  unescaped `</style>` in the stringifier. All are build-time-only for this repo
  (Next's internal CSS pipeline, running on your CSS), so real-world exposure is
  essentially nil. The direct `postcss` devDependency is already on 8.5.x and fine.
- **`next` declares `sharp` as `^0.34.5`**, and the fix is `0.35.0` — out of range.
  One high advisory, inherited libvips CVEs. On Vercel, image optimization is
  handled by the platform, so the bundled `sharp` mostly isn't the code path in
  production.

```json
"pnpm": {
  "onlyBuiltDependencies": ["@prisma/engines", "prisma"],
  "overrides": {
    "postcss": "^8.5.23",
    "sharp": "^0.35.3"
  }
}
```

Verified: installs clean, builds clean, output identical. The `sharp` bump crosses
a libvips major, so if you take it, eyeball a project page's thumbnail once. If you
would rather not carry overrides for build-time-only issues, **skipping step 3 is a
legitimate call** — just leave a note in `CLAUDE.md` next to the other "pinned on
purpose" entries saying these four are knowingly accepted and waiting on upstream.

## 2. Bugs

Ordered by how likely a visitor is to hit them.

### 2.1 Dates render one day early — **user-visible, everywhere**

`format(new Date('2024-09-20'), 'MMM dd, yyyy')` in `America/New_York` returns
**"Sep 19, 2024"**. A bare `YYYY-MM-DD` string is parsed by JS as UTC midnight;
`date-fns` then formats it in local time, which is 4–5 hours earlier — the previous
day for anyone west of UTC.

Verified with the site's real content:

```
2023-10-28  →  Oct 27, 2023   ✗
2024-09-20  →  Sep 19, 2024   ✗
2023-3-20   →  Mar 20, 2023   ✓  (non-ISO, so parsed as local time)
```

Every published date on the site is currently wrong by a day, *except* the ones
whose frontmatter happens to be sloppily formatted. Affected call sites:

- [blog/page.tsx:58](src/app/blog/page.tsx:58) — the `MM/dd` in the post list
- [blog/[slug]/page.tsx:93](src/app/blog/[slug]/page.tsx:93) — "Published on …"
- [portfolio/[slug]/page.tsx:96](src/app/portfolio/[slug]/page.tsx:96) — project date
- [(home)/page.tsx:65](src/app/(home)/page.tsx:65) — featured project year
- [content.ts:145](src/lib/content.ts:145) — **year bucketing on the blog index.** A
  post dated Jan 1 lands in the previous year's group and gets rendered under the
  wrong heading.

**Fix**, two parts, both required:

1. Normalize the frontmatter to zero-padded ISO. `grapple-grub.mdx` has
   `date: '2023-3-20'` and `player2-helpdesk.mdx` has `'2023-5-24'`; those are not
   valid ISO 8601 and `parseISO` rejects them.
2. Add a single `parseDate` helper in `src/lib/content.ts` using
   `parseISO` (which correctly treats a date-only string as *local* midnight) and
   route every call site through it. Verified: `parseISO('2024-09-20')` →
   "Sep 20, 2024".

Consider also validating frontmatter with Zod at parse time (see §4.2) so a
malformed date fails the build instead of silently rendering wrong.

### 2.2 Portfolio search crashes on regex metacharacters

[highlighted-text.tsx:16](src/components/highlighted-text.tsx:16):

```ts
const parts = text.split(new RegExp(`(${highlightedString})`, 'gi'));
```

`highlightedString` is raw user input from the portfolio search box. Type a single
`(` and this throws during render:

```
SyntaxError: Invalid regular expression: /((/gi: Unterminated group
```

The component renders inside a client tree with no error boundary, so the portfolio
page goes blank (dev: the error overlay). `[`, `*`, `+`, `?`, and a trailing `\`
all do the same. Non-crashing metacharacters are also wrong — typing `.` highlights
every character.

**Fix:** escape the term before interpolating, and bail on empty:

```ts
const escaped = highlightedString.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
```

### 2.3 Featured projects sort backwards

[content.ts:89](src/lib/content.ts:89) uses `(new Date(b.date) > new Date(a.date) ? -1 : 1)`,
which is the inverse of the comparator [content.ts:64](src/lib/content.ts:64) uses for
`getSortedProjects`. The docstring says "newest to oldest"; it sorts oldest first.

Confirmed in the built HTML — the home page currently lists `player2-helpdesk`
(2023-05) above `iconio` (2023-10).

**Fix:** use the same comparator as `getSortedProjects` — or better, delete
`getFeaturedProjects` entirely and have the home page call
`getSortedProjects().filter(p => p.featured)` (see §3.2).

### 2.4 Any non-`.mdx` file in a content directory becomes a slug

[content.ts:23](src/lib/content.ts:23) and [content.ts:98](src/lib/content.ts:98) map
`readdir` output through `.replace(/\.mdx$/, '')` with **no filter**. Verified: drop
a `.DS_Store` into `src/content/posts/` and `getAllPostSlugs()` returns
`[".DS_Store", "commonly-used-functions", "handle-form-loading-states"]`.

`getSortedPosts` then reads and `matter()`-parses it, producing an entry with an
undefined `publishedDate`, which makes `format()` throw a `RangeError` and takes
down `pnpm build`. This is a macOS repo; Finder creates `.DS_Store` files
constantly. Git ignores them so CI is safe, but a local build can break for a
reason that looks like nothing.

**Fix:** `files.filter((f) => f.endsWith('.mdx'))` before the map, in both functions.

### 2.5 The contact form is an unauthenticated email relay

[contact-actions.ts](src/actions/contact-actions.ts) has no rate limiting, no
honeypot, and no captcha. A server action is a public POST endpoint — anyone can
script it and burn through your Resend quota or fill your inbox. Nothing has
happened yet because the site is low-traffic, but this is the one genuine security
gap in the codebase.

**Fix**, cheapest first:
1. A hidden honeypot field that must stay empty — stops essentially all naive bots,
   costs five lines and zero dependencies.
2. Cap `message` length in `ContactSchema` (currently unbounded — `min(1)` only).
   `src/lib/utils.ts` already has an unused `validateString(value, maxLength)`
   helper that was clearly meant for this.
3. IP or session rate limiting. You already have Postgres and a session-cookie
   pattern in `post-actions.ts`; a small `contact_submissions` table reusing that
   approach avoids adding Upstash/Redis.

Related: the sender is `onboarding@resend.dev`, Resend's **shared sandbox domain**.
It works today only because `to:` is your own account address, and it's heavily
rate-limited with poor deliverability. Verify a domain and send from
`contact@ryangan.me`.

Also worth noting on the other action: `recordPostViewAction` validates the slug
(good), but a client rotating its cookie can inflate a count and add unbounded rows
to `post_view_sessions`. `CLAUDE.md` already notes the table is never pruned. Low
stakes for a view counter — just be aware the number is decorative, not audited.

### 2.6 Discord copy button isn't a button

[contact-info.tsx:62](src/components/contact/contact-info.tsx:62) is a `<span>` with
an `onClick` and an `aria-label`. It isn't focusable, doesn't respond to Enter or
Space, and `aria-label` on a non-interactive element is ignored by most screen
readers. Keyboard and screen-reader users can't copy the Discord ID at all.

**Fix:** `<button type="button">`. One-line change.

### 2.7 Every project thumbnail is marked `priority`

[project-preview.tsx:37](src/components/portfolio/project-preview.tsx:37) sets
`priority` on all grid images, which disables lazy loading and emits a high-priority
preload for each. With three projects it's harmless; it scales badly and it's
already costing LCP on the portfolio page. Both `[slug]` pages also mark the remote
avatar `priority` even though it's a 40px decoration.

**Fix:** `priority` on at most the first one or two cards (`index < 2`), and drop it
from the avatars.

### 2.8 `Callout` variants are unreadable in dark mode

[callout.tsx:17-20](src/components/callout.tsx:17) — `warning` and `danger` apply
`bg-yellow-50` / `bg-red-50` with no `dark:` counterpart, so dark-mode text would be
near-black on near-white. Nothing currently passes `type`, so it's latent. Either add
the dark variants or drop the prop.

## 4. Architecture and refactoring

### 4.1 `src/lib/content.ts` reads the disk far more than it needs to

Four functions each independently `readdir` + `readFile` + `matter()` the same
files. Rendering one blog post costs 4 filesystem reads: `generateMetadata` calls
`getPostData` (→ `getAllPostSlugs` + `getPostBySlug`), then the page component calls
it again. `getSortedProjects` and `getFeaturedProjects` are near-identical
copy-paste that differ only in a `.filter` — and their sort comparators have
already drifted apart (§2.3), which is exactly the bug duplication produces.

Two fixes, independently useful:

- **Wrap the readers in React's `cache()`.** `getAllPostSlugs`, `getPostBySlug`, and
  friends are pure per-request; `cache()` dedupes the `generateMetadata`/page pair
  for free.
- **Collapse `getFeaturedProjects` into `getSortedProjects().filter(p => p.featured)`.**
  Deletes a function, deletes the duplicated read loop, and fixes §2.3 by
  construction.

Extract one shared `readContentDir<T>(dir)` helper and both `posts` and `projects`
paths become ~15 lines each instead of ~40.

Build time is 5.7s so none of this is urgent — it's about not letting two copies of
the same logic drift again.

### 4.2 Frontmatter is cast, never validated

Every reader does `...(data as Omit<PostMetadata, 'slug'>)`. A `as` cast is a
promise to the compiler, not a check. Today the codebase contains an actual instance
of that promise being false: `ProjectMetadata.link` requires `github` and `live`,
and two of three projects supply only `live` (§2.9).

You already depend on Zod. Define `PostFrontmatterSchema` / `ProjectFrontmatterSchema`
and `.parse()` the `matter()` output. Malformed dates, missing `summary`, bad
`techStack` names then fail the build with a filename and a field, instead of
producing "Invalid Date" or a runtime crash on a page you forgot to check. This
would have caught §2.1 and §2.4 for free.

### 4.3 `TechStackIconName` and the icon switch

`tech-stack-icon.tsx` is a 328-line switch over a 45-member union, and callers reach
it via `tech as TechStackIconName` — an unchecked cast from a frontmatter string. A
typo in `techStack:` silently falls through to whatever the `default` branch is. A
`Record<TechStackIconName, IconType>` lookup map plus the Zod enum from §4.2 makes
the frontmatter the checked boundary and shrinks the file by ~80%.

### 4.4 Client/server boundary is slightly wider than needed

- `contact.tsx` is a client component whose entire job is a `framer-motion` opacity
  fade around two children. Replace with CSS and it becomes a server component;
  `ContactForm` (which genuinely needs `'use client'`) stays client.
- `ProjectList` is a client component because of the search box. Fine at three
  projects. If the project count grows, consider moving the filter to a URL search
  param so results are shareable and the list can stay server-rendered.

### 4.5 The Prisma schema carries three tables nothing uses

`User`, `Account`, and `GuestbookNote` exist only so `prisma db push` doesn't drop
them — which `CLAUDE.md` explains well. Worth an explicit decision rather than
indefinite limbo: if Auth.js and the guestbook aren't coming (see §5.5), drop the
tables in a migration and delete the models. If they are, they're fine where they
are. Right now they're 40 lines of schema and a standing "don't touch" note.

### 4.6 There are no tests

Zero test files, no test runner. Not a problem for a personal site, and I would not
recommend chasing coverage. But two pure functions are worth ~30 lines of Vitest
because they encode real logic and both have already had bugs:

- `getReadingTime` — the prose/code split calibration
- the date parsing/sorting helper from §2.1, with an explicit non-UTC timezone

### 4.7 Missing production hardening

`next.config.mjs` sets no `headers()`. For a static personal site the exposure is
low, but a small block costs nothing and is the sort of thing a reviewer looks for:
`Strict-Transport-Security`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`. A CSP
is more work with Next's inline scripts — treat it as optional.
`poweredByHeader: false` while you're in there.

## 5. Enhancements and features

Ordered by value-for-effort.

### 5.1 SEO essentials that are simply absent — **highest value, lowest effort**

The site has **no `sitemap.ts`, no `robots.ts`, and no per-page OpenGraph metadata**.
Every blog post and project page shares the site-level title and description, so
every link shared on LinkedIn, X, or Slack shows the same generic card. For a
portfolio whose entire job is being shared and found, this is the biggest gap in the
audit.

- `src/app/sitemap.ts` — enumerate routes from `getAllPostSlugs()` /
  `getAllProjectSlugs()`. ~20 lines.
- `src/app/robots.ts` — allow-all plus a sitemap pointer. ~10 lines.
- Per-post/per-project `openGraph` in the existing `generateMetadata` functions:
  real `title`, the frontmatter `summary` as `description`, `type: 'article'`,
  `publishedTime`, and the project `thumbnailUrl` as the OG image. The functions
  already fetch the data — they just don't use it.
- Dynamic OG images via `opengraph-image.tsx` in each `[slug]` segment: title +
  date + reading time rendered by `ImageResponse`. Much bigger visual payoff than
  the effort suggests.
- JSON-LD `BlogPosting` / `Person` structured data in the post layout.

### 5.2 RSS feed

A blog with no feed. `src/app/feed.xml/route.ts` reading `getSortedPosts()` is
~30 lines and makes the blog followable. Pairs naturally with the sitemap work.

### 5.5 Guestbook or comments — decide, then act

There's a `GuestbookNote` table with no rows, `User`/`Account` tables for an Auth.js

started and never finished.

Either build it (Auth.js with GitHub OAuth, the tables are ready, and the view-counter
code already establishes the fails-soft + session-dedup patterns to follow) or delete
